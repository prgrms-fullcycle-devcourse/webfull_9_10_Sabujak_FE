
# Sabujak Project - LLM 활용 가이드라인 (llm_guide.md)

## 1. 목적 (Purpose)
본 문서는 사부작(Sabujak) 프로젝트 팀원들이 
ChatGPT, Gemini, Claude 등의 LLM을 활용하여 코드를 작성하거나 디버깅할 때, 
일관된 아키텍처를 유지하고 보안 사고를 방지하며 
팀 전체의 코드 품질을 상향 평준화하기 위한 표준 지침을 제공합니다.

## 2. 절대 보안 수칙 (Security First)
LLM에 프롬프트를 입력할 때 다음 정보는 **절대 포함해서는 안 됩니다.**
* **인프라 자격 증명:** `.env` 파일의 내용, DB 접속 URI (Neon DB), JWT Secret Key.
* **클라우드 키:** 외부 API 발급 키, 배포 플랫폼(Render) 토큰.
* **해결책:** 에러 로그나 코드를 복사하여 붙여넣기 전, 
반드시 비밀번호나 토큰 값을 `***` 또는 `<REDACTED>`로 마스킹 처리하십시오.

## 3. 사부작 프로젝트 공통 시스템 프롬프트
LLM에게 코드를 요청할 때는 항상 우리가 사용하는 기술 스택과 아키텍처 원칙을 
먼저 주입해야 합니다. 
새로운 채팅을 시작할 때 아래의 텍스트를 복사하여 가장 먼저 입력하십시오.

> **[Sabujak 공통 시스템 프롬프트]**
> 너는 대용량 트래픽과 데이터 무결성, 그리고 최적의 UX를 고려하는 시니어 풀스택 개발자야. 
다음 기술 스택과 원칙을 엄격하게 지켜서 코드를 작성해.
> 
> 1. **Tech Stack:** 
	> - Backend: Node.js, Express, TypeScript, Drizzle ORM, Zod
	> - Frontend: React, TypeScript, Vite, Tailwind CSS, Zustand, TanStack Query v5, Orval
> 2. **Frontend Rules:** 
			스타일링은 반드시 Tailwind CSS 유틸리티 클래스를 사용하고, 
			환경 변수는 Vite의 `import.meta.env` 규격을 따라야 해.
> 3. **Validation & Type Safety:** 
			모든 외부 입력은 Zod 스키마로 검증하며, 
			프론트엔드와 백엔드 모두 `any` 타입 사용을 엄격히 금지해.
> 4. **Database (Drizzle):** 
			시스템 내부 PK는 `ULID`를 사용하고, 사용자 노출 URL은 `slug`를 사용해. 
			모든 날짜는 타임존이 포함된 `timestamptz`로 설정하여 UTC 기준으로 저장해.
> 5. **Error Handling:** 
			에러 발생 시 백엔드는 명확한 HTTP 상태 코드(400, 401, 404, 409 등)로 응답하고, 
			프론트엔드는 이를 사용자 친화적인 UI 텍스트로 풀어내야 해.

## 6. 코드 리뷰 및 반영 원칙
* LLM이 생성한 코드는 완벽하지 않으며, 특정 엣지 케이스를 누락하거나 보안 취약점을 유발할 수 있습니다.
* 복사 및 붙여넣기 전, 반드시 **타입 안정성**, **예외 처리 로직(try-catch)**, **비즈니스 요구사항 일치 여부**를 스스로 확인하고 팀원과 교차 검증(Code Review)해야 합니다.


#해야할 업무 관련 회의내용
1. 라우터 구조 잡기
2. 필요한 패키지 깔기
3. 린트 어디까지 허용하고 어디까지 잡을건지 셋팅
    - unused vars 에러로 볼지 경고로 볼지
        - 1. unused vars는 에러로 두는 곳 거의 없음 다 경고로 보고 워닝도 린트에러로 잡히게 린트에서 설정해두던가 하셈 초반에는 변수 중복이나 이런거 개많음, 팀원들이 개발 실무 오래한 사람들 아니니까
        - 1번 에러로 걸면 진짜 사소한거에서 시간 너무 잡아먹음
    - any 허용할지
        - 2번 애니는 제한적으로만 허용해야함. 피치 못할 때는 사용하되, 린트에서 제한해놓으면 이것도 이딴거에 시간 너무 많이 씀
    - console.log 허용 범위
        - 3. 콘솔로그는 허용하되, 개발 환경에서만 쓰고 커밋전에 빼기
    - default export 허용 여부
        - 디폴트 익스포트는 취향임
        나는 컴포넌트는 쓰고 그 ꖶዞ 훅이나 유틸이나 컨스턴트 같은건 걍 네임드 씀
    - 절대경로 import 강제할지
        - 5. 절대경로는 아까 말했지만, 솔직히 큰 쓸모는 없는데 난 상대경로 쓰는거 싫어함 개더러워
    - 파일/폴더 네이밍 규칙
        - 네이밍 규칙 -> 취향
        근데 훅같은건 뭐 useDDDFFF.ts 이렇게 쓰면 댐
        - 데이트 유틸이다, 이러면 formatDate.ts
        컴포넌트파일 네이밍은 파스칼케이스로 추천함
    - hooks 규칙 외에 import 순서, type import 분리까지 볼지
        - 7. 임포트 순서는 자동화 해놓으셈 익스텐션이었나 있음
    
    즉 “eslint 설치”가 아니라 “팀 규칙 문서화”가 핵심이에요.
    
    보통은 너무 빡세게 시작하지 말고, 빌드 깨지는 규칙만 먼저 error, 스타일 취향은 warn으로 시작합니다

    - 한 페이지에서만 쓰는 값: local state
    
    이 경계만 팀에서 먼저 합의해도 초기세팅이 훨씬 깔끔해집니다.
